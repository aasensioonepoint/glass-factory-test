## Gated chain

The pipeline above is one chain with two adversarial gates and a single human one. Route it in this shape, never a shorter one:

```
planner → plan-critic (PLAN, critique UNIQUE, son verdict EST le verdict ; indisponible : COVERAGE DEGRADED, verdict absent)
                             ──NO_GO──> planner reprend son plan avec les constats du critique (S-01M4TZZ13Y)
                             (max 8 itérations de critique, puis escalade humaine)
              │ GO / GO_AVEC_RESERVES
              ▼  [GATE humain unique]
   dev(-mono | -multi | frontend-fidelity | terraform-deployer)
              │
              ▼
   exec-critic (EXÉCUTION) ∥ securite, même diff ; NO_GO/findings ──> dev, qui relance les deux
   securite = security-code-review  (code produit — class-1, jamais waivable)
            + security-orchestrator (si un manifeste de dépendances a bougé)
              │  RÉGIME EN VIGUEUR AUJOURD'HUI : systématique, les deux, jamais contourné
              │  RÉGIME CIBLE À PARTIR DE P5 : ──findings sensibles──> securite (règle 3)
              │  class-0 gitleaks : actif dans les deux régimes (règle 4)
              │ GO
              ▼
   build_index --if-stale (0-LLM) → documenter
     → indexer? → revue critic-opus (repli fable, puis sonnet-max) → corrections
     → porte verify.sh --at HEAD → tasks.py done → livraison
                                          │
                                          └── LECON_CANDIDATE → retro/LESSONS.md
```

The `documenter` at the tail of this chain runs AFTER a dev agent: hand it the dev agent's diff summary as its `Dev agent's diff summary (if post-change)` input — without it the documenter treats the call as the docs-only route and refuses source-file writes (docstrings, inline comments).

**Closing review — NO TASK IS MARKED DONE WITHOUT A CRITICAL REVIEW** (AGENTS.md § Golden rules). Steps 15-17 are the chain's last links, in THIS order: `work → review → FIX its findings → gate bash core-scripts/verify.sh --at HEAD → tasks.py done T-NNN --raison "<why>"` (`--at HEAD` alone is this kit repo's local waiver, AGENTS.md § Verifying before a push; `--at HEAD` in an adopter, whose gate is `porte_adoptant.py` (project and submodules) and where `--linux` has no object; never the bare form: it stamps `mode=live`, refused at push and invisible to the borrow window) — the review precedes the gate, and `done` comes only after both; a gate that went green BEFORE the review proves nothing about the closure. FIX means: route the findings to the task's dev-* agent (fix pass: `kind=delta`, replay `security-code-review` on the fix diff; `documenter` only if the fix touched what it documented; the review is not re-run — a borrowed proof's `done` records the reviewed SHA on the board, `[binôme relevé sur T-… @ <sha>]`, and a task closed on its own trace cites that SHA in `--raison`, so the reader sees the corrections came after). ONE closing critic for every closure (pilot decision S-00004500): `critic-opus`; if it is unavailable (quota, outage) the fallback is IMMEDIATE — `critic-fable`, then `critic-sonnet-max` at maximum effort (on Claude Code, `critic-fable` shares `critic-opus`'s model, so an exhausted Opus quota takes both down and the fallback that survives is `critic-sonnet-max` — go straight to it) — and the critic, alone, carries angles A and B (structure, state, side effects; business logic, regressions, unverified assumptions). ## Repo-wide (sharded) mode
A migration, rename, or cross-cutting sweep that spans many modules must NOT become
one mega-plan (planner caps at 8 steps for a reason). Shard it by module, reusing the
per-module grouping `build_index.py` emits, and emit a SHARDED PLAN instead of PIPELINE:

```
SHARDED PLAN (repo-wide — <N> modules)
  shard 1  <module/path>   <one-line per-module sub-task>   ~Nk
  shard 2  <module/path>   …                                ~Nk
  …
  WAVES: [1,2,3,4,5,6] [7] …      # ALL independent shards in one parallel wave; a later wave only for shards depending on an earlier one
  RECONCILE: <cross-shard verify/merge sub-task>            ~Nk
  TOTAL (rough)                                             ~Nk ±50%
```
- Enumerate modules from `CODEBASE_INDEX.md` Modules / the `SYMBOLS_<module>.md` shards. One shard = one module's slice of the change.
- Each shard runs the SAME gated chain as any other task — `planner` → `plan-critic` → `[GATE humain unique]` → `dev-*` → `exec-critic` ∥ security → `build_index --if-stale` → `documenter` — scoped to its module only, so each stays within the 8-step / context limits. **Sharding narrows the SCOPE, never the chain**: no shard skips `plan-critic` or `exec-critic`, and repo-wide is the mode this repo runs most, so an exemption here would exempt almost everything. The per-shard chain ENDS at `documenter` (and `indexer`); the closing review, its fixes, the gate and `tasks.py done` run ONCE per wave, serially, on the union of the wave's diffs — never one gate per shard in parallel (a critic's trace credits every `running` member of the group). Every `done` of the wave follows ONE frozen green; the push gate on the post-`done` state commit comes AFTER the last `done`, or every borrowed proof expires. RECONCILE is the terminal wave: its own review → fixes → gate → `done`.
- Throughput via MAXIMAL fan-out, in waves of at most the `PEUT_AJOUTER` of `charge_poste.py verdict`: run every independent shard in parallel; sequence only shards that touch the same files or consume another shard's output. State the wave layout.
- The RECONCILE shard checks cross-module seams (shared types, call sites that crossed module lines) after all shards land.

## Hard rules
- Fan out independent subagents in parallel — one message per wave of at most `PEUT_AJOUTER` (`charge_poste.py verdict`) — whenever stages do not depend on each other; token cost is never a reason to sequence.
- If the request is ambiguous, ask ONE clarifying question before routing.
- After the routing plan is emitted, hand it to the parent and STOP ROUTING. **Do not stop for approval at this stage**: the `planner` owns the approval gate, and the `[GATE humain unique]` sits after `plan-critic`, not after this routing plan. One human gate in the chain, never two — a routing plan is a hand-off, not something to have approved.
