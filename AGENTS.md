## Golden rules
- NEVER read files fully unless required. Read `.agents/state/index/CODEBASE_INDEX.md`, then LOCATE by NAME, then read only the line ranges you need. **A locator is not an authority**: re-locate by name before trusting any `path:start-end`. → `.agents/skills/codebase-indexing/SKILL.md`
- Delegate heavy work when the host supports subagents: search, analysis, and refactors over 3 files stay out of the main context — and fan independent subagents out IN PARALLEL (one message per wave, at most the `PEUT_AJOUTER` of `charge_poste.py verdict`) rather than sequencing them.
- Pipeline mandatory for any task touching 6 files or more, or any task `tasks.py direct` refuses (one it admits takes the DIRECT path below): cadrage (cadrage_plan.py) → `language-detector` → `planner` → **le CRITIQUE DE PLAN UNIQUE (`plan-critic` ; au `NO_GO`, le planner reprend son plan avec ses constats ; indisponible : `COVERAGE DEGRADED`, verdict absent — S-01M4TZZ13Y)** → (human approval) → `dev-*` → `exec-critic` ∥ security gate, EN PARALLÈLE sur le même diff (S-01M551RDK3PRT4VGTV5BN1ZM30 ; where the host launches subagents together (measured: Claude Code); elsewhere in series, exec-critic first, the fix still waiting for both verdicts ; exec-critic rejoue chaque critère d'acceptation avec une sortie réelle ; `security-code-review`; + `security-orchestrator` if a dependency manifest moved ; exec-critic compte au verdict de charge, une place : exec-critic d'abord, S-01M559V3Y1KNXD4JQJNQ735AJH ; security-orchestrator avec les places qui restent une fois qu'exec-critic tient la sienne ; la correction attend les DEUX verdicts, toute passe de correction relance les deux (hors la correction de clôture)) → deterministic index rebuild (`build_index.py --if-stale`, 0 LLM) → `documenter` → `indexer` if structure changed → **revue de clôture à UN critique (`critic-opus`, repli `critic-fable` puis `critic-sonnet-max`) → correction de ses constats → porte `verify.sh` → `tasks.py … done`**. Les quatre derniers maillons sont dans CET ordre : la revue précède la porte, et `done` ne vient qu'après les deux.
**On a UI task the dev slot is `frontend-fidelity`, and `design-review` runs after it, before the human gate** (on the direct path, which has none: before the closing review) — the implementer cannot certify its own fidelity. A UI task carries a mockup or asks for visual work. → `.agents/skills/frontend-fidelity/SKILL.md`
On an IaC task (`*.tf`, `*.tf.json`, `*.tfvars`, `*.tfvars.json`, `.agents/deploy/targets.json`) the dev slot is `terraform-deployer` ; exec-critic, security-code-review and the closing review run on its diff like any dev-* ; it never applies in the same task — apply is the separate, out-of-chain deploy after `done` and a green gate frozen on that SHA, through `tfdeploy.py`, on a decision it does not write. → `.agents/skills/terraform-deploy/SKILL.md`

**Un plan qui touche l’écran NOMME SON MOCKUP ou DÉCLARE SON ABSENCE** — une seule de trois valeurs fermées : `mockup: <chemin ou nœud>`, `no mockup: <raison>`, ou `mockup not reproduced: <chemin> + <tâche qui EXISTE au board>`. `plan-critic` **REFUSE** un plan d’écran qui omet la ligne. Il porte AUSSI sa spec d’interaction, `INTERACTION: focus=<…> ; echap=<…> ; modal=<…> ; empilement=<…> ; wcag=<…> ; largeurs=<…> ; etats=<…>` ou `INTERACTION: sans objet | <motif>` (S-01M5N24P2Y0SH6S0W0YNG3TAN6) : deux contrôles UI bloquent, la ligne mockup et la ligne INTERACTION ; `frontend-fidelity` l’applique, rend au parent tout arbitrage qu’elle ne couvre pas, et joue les 8 phases de `design-review` avant de rendre (`GRID:`). Une source de design qui EXISTE se reproduit, jamais ne se réinvente. → détail : `.agents/skills/frontend-fidelity/SKILL.md`
plan-critic runs after planner and before the single human approval gate; a NO_GO returns the plan to planner, which revises it with the critic's findings, for at most 8 critic iterations total, one iteration being plan-critic on one plan, after which the task is blocked and escalated to the human — plan-critic writes nothing.
`GO_AVEC_RESERVES` proceeds to the same single gate and never loops; `GO` likewise. On a host where the critic is unavailable the gate carries `COVERAGE DEGRADED — plan-critic unavailable, verdict absent` instead of blocking — never a false GO, never a frozen pipeline.
**At exhaustion only** (8/8, still NO_GO) the escalation carries the correcting plan line already written for every blocking finding closable without new investigation — no new gate. → `.agents/skills/planning/SKILL.md`
**PRÉFLIGHT DE FORME** (S-01M57JCYTZ) : avant chaque `plan-critic`, l'exécuteur joue `plan_preflight.py --plan "<plan>" --task <T>` et relaie sa sortie brute ; rc 1 rend le plan au planner sans compter d'itération (second rc 1 consécutif : le pilote), rc 2 = `COVERAGE DEGRADED`. Forme seule : aucun banc rejoué, aucune donnée du plan exécutée ; la ligne `PREFLIGHT:` du plan ne prouve rien. → `.agents/ref/PLAN_GRAMMAIRE.md` § 5
**PLAFOND DU CRITIQUE DE PLAN** (décision pilote S-01M4V7RGDPP6ZK64NQ0RMN7BEN) : le cap de 8, ci-dessus et sous « UN SEUL CRITIQUE DE PLAN », vaut DANS LE KIT ; chez l'adoptant, le plafond N vaut 2 par défaut, relevé seulement sur demande explicite de son pilote, qui édite N À LA MAIN dans `.agents/state/gates/PLAN_CHAIN_REQUIRED`. L'exécuteur le lit avant chaque `plan-critic` et après chaque verdict journalisé de la boucle : `bash .agents/pyrun.sh .agents/bin/plan_plafond.py --task T` imprime `PLAFOND=<N> SOURCE=<kit|adoptant|adoptant-illisible>` (ou `decoupe` : tâche découpée du kit, plafond 2 par plan, escalade comme chez l'adoptant — kickoff SKILL § 8c) puis `ITERATION=<n> ALLOCATION=<a> ESCALADE=<oui|non>`, que le CODE calcule (n : verdicts `plan-critic` du cycle ; a : N + prolongations du cycle, dédoublonnées par l'itération qu'elles ouvrent — une prolongation journalisée deux fois n'en accorde qu'une ; `ESCALADE=oui` : dernier verdict compté ni une approbation (GO, GO_AVEC_RESERVES, PASS/CONCERNS historiques) — NO_GO ou titre illisible — et n ≥ a) ; aucune ligne `PLAFOND=` lisible : plafond 2, jamais « kit » ; ligne 2 absente ou illisible : `ESCALADE=oui` — les deux avec un avertissement au pilote. Hors du kit (`SOURCE=adoptant` ou `adoptant-illisible`), CHAQUE verdict plan-critic de la boucle, NO_GO compris, est journalisé UNE fois AVANT le compte. Cette entrée EST celle que la surface écrit déjà pour ce verdict — « Record the critic's verdict » (kickoff SKILL étape 6), ou le checkpoint NO_GO de /planning avec son `--text` plan=/revision=/status=/sha256= — sous le titre `plan-critic <VERDICT> (iteration <n>/<N>)`. Jamais une seconde entrée : le « Record the FINAL verdict » de fin de boucle (kickoff.md:179) n'en rajoute pas. La permission du titre suffixé ne vaut plus pour un verdict de boucle. Invoquer plan-critic avec `itération <ITERATION+1>/<PLAFOND>`. Au `reopen` ou à la replanification d'une tâche déjà jugée : `specs.py add --task T --kind decision "plafond critique : nouveau cycle"` avant le premier plan-critic. `SOURCE=kit` : l'exhaustion à 8/8 ne change pas. L'escalade au plafond est RÉSERVÉE à `SOURCE=adoptant*` ou `decoupe`, avec `ESCALADE=oui`, et son pilote y tranche : sous `$kickoff`, `tasks.py block T --note "plan-critic NO_GO x<n> (plafond <N>) — <k> unresolved blocking findings"`, puis `communicator` en mode décision — (1) continuer une itération de plus, (2) réduire, (3) lever un constat nommé, (4) abandonner ; sans réponse, la tâche reste bloquée ; sur (1), `specs.py add --task T --kind decision "prolongation plafond critique : itération <n+1>"`, `tasks.py unblock T`, puis une nouvelle itération — la même question revient à chaque NO_GO suivant. Sous `$planning` et `$planning-all`, jamais de block ni d'unblock : la tâche sort du pool, et l'escalade, option « continuer une itération de plus » comprise, est DITE au rapport. → détail : `.agents/skills/kickoff/SKILL.md`, `.agents/skills/planning/SKILL.md`

- **UN SEUL CRITIQUE DE PLAN** (décision pilote S-00003871, 2026-10-03 — remplace la paire de critiques de plan ; planification sur Opus seul depuis S-01M4TZZ13Y, 2026-10-13) : `plan-critic` (claude-opus-5-5, high) relit le plan ET en attaque les PRÉMISSES — rejouer les mesures décisives, exiger des témoins capables de rougir, muter aussi les valeurs par défaut ; son verdict EST le verdict (`GO` / `GO_AVEC_RESERVES` = approbation, `NO_GO` = révision) — `NO_GO` pour un constat BLOQUANT seul (exécuté tel quel, le plan livrerait faux, casserait une garde ou un filet, ou repose sur une prémisse réfutée par mesure ; un plan de plus de 45 lignes non vides, `plan_lots.py check` rc 1, est un bloquant de forme, comme une ligne `PREFLIGHT:` absente ou une sortie rc 0 de `plan_preflight.py` non relayée, sauf rc 2 relayé sous `COVERAGE DEGRADED`) ; une réserve ne justifie jamais un `NO_GO`, elle part à la passe de correction du dev (R2 ; décision pilote S-01M52Y43BA) ; au `NO_GO`, `planner` reprend son plan avec les constats du critique ; le cap de 8 compte les itérations de `plan-critic` (la « critic iteration » de la phrase canonique : un plan soumis au critique). Chaque verdict de boucle journalisé porte le chrono du tour, `chrono: planner=<durée>/<jetons> plan-critic=<durée>/<jetons>` (sur Claude Code, `--chrono-aid ROLE=<agentId>` pour chaque rôle qui y a tourné, écrit depuis le journal des agents, jamais à la main ; un rôle routé ailleurs (Codex) : `--chrono-aid ROLE=<durée>/<jetons>` mesurés, jamais 0, ou `--sans-chrono`), que `specs.py add` EXIGE sous `.agents/state/gates/CHRONO_REQUIRED` (sortie tracée `--sans-chrono "<pourquoi>"`, visible) et que `specs.py chrono` relit — tours, durée et jetons par tâche, médiane et p90 (décision pilote S-01M534MZK4). `plan-critic` indisponible (quota Opus) : aucun autre critique de plan ne le remplace, la porte porte `COVERAGE DEGRADED — plan-critic unavailable, verdict absent`. **AU MOINS UN critique domine le planner sur chaque axe** : `plan-critic` (claude-opus-5-5, high) domine `planner` (claude-opus-5-5, medium) ; sur Claude Code, il le domine par l'effort, à égalité de modèle ; l'abaisser sous le planner casse la règle. `planner-sonnet` et `plan-critic-sonnet-max` sont HORS CHAÎNE (S-01M4TZZ13Y) : défs gardées sur disque, jamais invoquées ; les traces des deux défs hors chaîne (S-01M4TZZ13Y) restent acceptées par la garde, sans échéance ; chaque trace expire 24 h après son écriture, comme toute trace. Le refus mord sur `tasks.py start` (armé par `PLAN_CHAIN_REQUIRED` : au moins UN critique de plan et un plan tracés ; une tâche dont l'estampille `tasks.py direct` tient au rejeu démarre sans chaîne et n'en consomme aucune ; sortie tracée `--sans-chaine "<pourquoi>"`) : il empêche d'OUBLIER, pas de TRICHER. → détail : `.agents/skills/planning/SKILL.md`, `.agents/skills/task-board/SKILL.md`
- **LA CIBLE DE PLAN** (armée par `PLAN_CIBLE_REQUIRED`, pour le chantier de la ligne `chantier=`) : chaque étape porte `cible: « <nom> »`, `angle mort: <question au pilote>` ou `décision pilote: S-<id>`, sinon le plan est incomplet ; sortie tracée `--sans-cible "<pourquoi>"`. Une tâche SANS plan approuvé dont l'estampille `tasks.py direct` tient au rejeu passe le `done` sans `--sans-cible` ; un plan résolu reste toujours contrôlé. La trace `plan approuvé` est AUTO-DÉCLARATIVE comme le verdict de la chaîne — elle n'empêche ni de citer à tort ni de déclarer approuvé un plan qui ne l'a pas été ; la jambe `specs.py` ne mord que sur un verdict TITRÉ `plan-critic …`, jamais sur les verdicts de paire titrés `T-… itération N : paire …`. - **LA VOIE DIRECTE, ADMISE PAR CODE.** `tasks.py direct <T>` estampille une tâche que le code VÉRIFIE ; estampillée, elle part au `dev-*` sans `planner`, ni `plan-critic`, ni porte humaine — restent `exec-critic` ∥ `security-code-review` (en parallèle), la revue de clôture, la porte et `done` ; sur une tâche d'écran, le slot dev est `frontend-fidelity` puis `design-review`, avant la revue de clôture, et la ligne `mockup:` / `no mockup:` se pose au stage avant `direct`, sa ligne `INTERACTION:` aussi (décision S-01M5R7MCST). Un refus liste TOUTES ses causes et n'écrit rien : C1 write-set DÉCLARÉ de 5 fichiers ou moins, en chemins exacts (ni glob ni répertoire), motif `gros` refusé ; C2 aucun chemin de garde (liste FERMÉE de `tasks_direct.py`), motif `garde` refusé ; C3 ni motif `decision-pilote` ni décision ouverte au titre ou au stage (lexique fermé), sauf dans le segment qui cite une décision tracée sur CETTE tâche ; C4 ni motif `securite`, ni lexique de sécurité au titre, ni dernier verdict de sécurité OUVERT de la tâche (titre ou texte : `NO_GO`, `FINDINGS(code)`, N HIGH/CRITICAL, rouge, bloque — un signal ouvert l'emporte sur `CLEAN`, `GO` ou `PASS` écrits à côté) ; tout motif autre que `sans-fournee` refusé ; SPECS illisible refusé. **Portée** : là où l'estampille FRANCHIT une garde ARMÉE (chaîne au `start`, cible au `done`), elle est REJOUÉE — critères, write-set courant inclus dans l'estampille, tâche non close — et la marque `[DIRECT SANS PLAN : …]` reste VISIBLE au board ; `reopen` garde l'estampille, rejouée au `start` suivant, sans la marque du cycle clos ; là où rien n'est armé, elle est inerte. Une directe ne consomme JAMAIS une chaîne, et l'emprunt d'un groupe parallèle ne la dispense jamais du rejeu. Retour au chemin planifié : `tasks.py direct <T> --retirer`, refusé sur une tâche non close dont la chaîne a été franchie (remède : `done`, ou `reopen` puis `--retirer`). Estampillée ou non, la garde de kickoff, là où son fichier de porte existe, arme aussi une tâche `running` dont un chemin du write-set est un chemin de garde, quel que soit son compte. **Borne de la liste** : elle couvre hooks et lanceurs, porte et CI (ce que leur config CITE, jamais ce que le script appelle), board et plan, graines et leur canal, les juges — défs d'hôte des cinq hôtes, sources `agents/<juge>.md` et roster `.agents/vendor/cadre/data/roster/<juge>.json` — et leur générateur (`render_hosts.py`, `.agents/vendor/cadre/renderers/` et leurs deux bancs), ses propres bancs, les noms de fichier de garde et l'IaC du projet (`*.tf`, `*.tf.json`, `*.tfvars`, `*.tfvars.json`, `.agents/deploy/targets.json`) ; elle ne couvre PAS `AGENTS.md`, les défs `dev-*`/`documenter`… (source et rendus), `commands/*.md` et ses rendus (`.claude/commands/*.md`, miroirs `source-command-*`), les rendus Cursor `.cursor/` (règles des juges comprises), ce que le générateur LIT sans en être (`core-scripts/apply-mode.py`, `.agents/vendor/cadre/roster.py`, `.agents/vendor/cadre/config.py`, `.agents/vendor/cadre/workspace.py`, en attente d'une décision pilote), `.gitignore`, les manifestes de dépendances, un banc qui teste une garde sans le dire dans son nom, ni les frères de `sync_template.py` (outil d'équipe du kit, qui ne voyage pas). **Non vu par le code** : (i) une décision ou une sécurité ouverte que ni le titre ni le stage n'écrivent ; (ii) un verdict de sécurité tracé sur un slot plutôt que sur la tâche, hors du `done` d'une directe qui franchit une garde armée, qui lit un `running` de sa portée ou de son groupe et marque l'emprunt ; (iii) le diff réel au-delà du write-set — au `done` d'une directe qui franchit une garde armée, seule la branche relevée est vue (sa fusion comprise) ; un commit posé hors d'elle ne l'est pas ; (iv) une chaîne jouée pour une tâche ensuite estampillée reste non consommée et couvre le prochain `start` planifié pendant 24 h ; (v) « petit » est prouvé, « inoffensif » jamais. Là où l'estampille franchit une garde armée, le `done` exige le relevé `tasks.py retour` d'une branche qui ne porte qu'elle, fusionnée `--no-ff` telle quelle, fichiers dans l'estampille, et un verdict de sécurité tracé après lui qui ne dit ni un blocage ni une revue absente, sur la tâche ou un `running` de sa portée ou de son groupe ; déclaratif, il empêche d'oublier, pas de tricher ; sortie tracée `done --sans-cible "<pourquoi>"`, visible au board ; ailleurs, `security-code-review` OBLIGATOIRE sur le diff de toute directe reste une règle de PROSE. → détail : `.agents/bin/tasks_direct.py`, `.agents/bin/tasks_retour.py`, `tasks.py direct --help`
- **AUCUNE TÂCHE N'EST MARQUÉE TERMINÉE SANS UNE REVUE CRITIQUE** (décision pilote S-00004500) : UN critique de clôture pour TOUTE clôture — `critic-opus`, repli immédiat `critic-fable` puis `critic-sonnet-max` (effort maximal) —, qui porte seul l'union des angles A et B ; sur Claude Code, `critic-fable` partage le modèle de `critic-opus` (claude-opus-5-5) : un quota Opus épuisé les rend indisponibles tous les deux, et le repli qui survit est `critic-sonnet-max` ; l'indépendance de deux modèles est ABANDONNÉE par décision, jamais affaiblie en silence. **Sa place est JUSTE AVANT la porte** : `travail → revue de clôture → CORRIGER ses constats → porte → done`. Objet : la DÉTECTION ACTIVE — un verdict seul est un refus de travailler ; chaque rapport porte trois blocs : trous repérés, trouvailles (`fichier:ligne`, cause racine, scénario), correctifs concrets (le code exact). `tasks.py done` REFUSE sans UN critique tracé par l'hôte (`BINOME_MIN`, armé ici par `BINOME_REQUIRED` ; emprunt de slot écrit au board, périmé à l'avant-dernier verdict vert (sans deux verts frozen : 24 h) ; sortie tracée `--sans-binome "<pourquoi>"` pour un doublon, un ticket caduc ou une décision sans code — la raison reste VISIBLE au board). - **L'AMONT D'ABORD** (décision pilote S-01M4Z5VMP5E9YN8T6EMDTBAF0T) : une tâche ne se planifie ni ne démarre avant ses amonts. `tasks.py deps-ready <T>` liste, amont d'abord, la fermeture transitive des amonts non `done` de son `depends_on` ; sa 1re ligne est `deps-ready: CYCLE|AMONT_OUVERT|INEXPLOITABLE|PLAN_A_REPLANIFIER|REPRISE_DITE|AMONT_CLOS`, le premier qui s'applique dans cet ordre, rc 0 (`AMONT_CLOS`, `REPRISE_DITE`) · 1 sinon · 2 usage. Tout `start` depuis `pending`, `blocked` ou `done`, et la `fournee`, REFUSENT `CYCLE`, `AMONT_OUVERT`, `INEXPLOITABLE` (avec un ancêtre `done` : `plan_cible` absent ou qui ne se charge pas, journal SPECS illisible ou trace sans date lisible — fail-closed) et `PLAN_A_REPLANIFIER` (un ancêtre clos à ou après la trace `plan approuvé`), sauf quand la tâche reprend sous la trace même qui l'a lancée et que chaque amont en cause était clos au plus tard à ce lancement (`REPRISE_DITE`) — un amont clos APRÈS le lancement rend `PLAN_A_REPLANIFIER` ; sortie tracée `--sans-dependances "<pourquoi>"`, décision du pilote, VISIBLE au board ; `done` ne refuse pas sur cette jambe, il DIT. Les lanceurs lisent le jeton AVANT `planner`/`plan-critic` et AVANT `start`/`fournee` : sur `AMONT_OUVERT`, STOP et `communicator` en mode décision, l'amont d'abord. **Borne** : seul un `depends_on` DÉCLARÉ est vu — une dépendance non déclarée ne l'est pas ; planner et plan-critic ne sont tenus que par leurs lanceurs ; une tâche déjà `running` n'est pas rejugée ; les bornes de la reprise (sans `lancee_le`, cause sans `done_at` ou illisible, arbre sans ce code) sont au task-board.
