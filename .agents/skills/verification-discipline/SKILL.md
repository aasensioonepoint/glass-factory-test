# Verifying before a push

Moved VERBATIM out of `AGENTS.md` (P4 — the router becomes thin, the rules do
not change). The router keeps a short invariant and points here for the detail.

`bash core-scripts/verify.sh` runs the CI's SCOPE; `--linux` additionally replays it inside ubuntu via Docker, in CI's BARE form by default (`docker run` passes `CADRE_GATE_JOBS`, defaulting to `1`; a value the caller exports wins). Locally the gate runs pytest through `core-scripts/run-pytest-shards.sh` (parallel slices over the collection `pytest.ini` defines) and the bash suites in parallel through `run-bash-tests.sh`; CI pins `CADRE_GATE_JOBS: "1"` and runs the bare commands (`python -m pytest`) — so the parallel gate is a LOCAL-gate path, the bare one the CI path, and neither is measured as the other. Knobs, all optional: `CADRE_GATE_JOBS` (`auto` = cores/2 capped at 12, the default; `1` or `0` = the bare command, the adopter's FIRST remedy when the parallel gate misbehaves; `8` restores the former cap), `CADRE_GATE_JAMBES` (`auto` default | `serie` | `parallele`: under `auto` the kit gate plays its pytest and bash legs AT THE SAME TIME only when `CADRE_GATE_JOBS` is empty or `auto`, outside MINGW/MSYS/CYGWIN, on 16 cores or more — same commands, same verdict, same stamp; read then unset, never inherited by a suite), `CADRE_GATE_JOBS_BASH` (job count of the bash leg alone, wins over `CADRE_GATE_JOBS` for that leg; integer ≤ 64, `auto` refused; the pytest leg's `auto` cap is 12, while the bash leg stays capped at 8 in series and at min(4, cores/4) in parallel unless `CADRE_GATE_JOBS_BASH` is set), `CADRE_GATE_CHUNK` (slice size), `CADRE_GATE_BASE` (default `HEAD~1`: files changed since run first), `CADRE_GATE_FAIL_FAST` (`prio` default | `all` | `0`; it now also stops the LATER steps of `verify.sh` and its `--linux` leg at the first red — reported `NOT RUN`, never green; `0` plays everything; CI does not call `verify.sh`), `CADRE_GATE_DURATIONS_DIR` (default `.agents/state/local/porte-durees/`: per-unit durations the two runners write after a run and read on the next one, to ORDER and SLICE the work — never to decide a verdict; under `--at` the frozen clone writes them into the live tree; the effect starts at the second gate), `CADRE_GATE_REPLAY` (default 3: a red of VERDICT under the pool is replayed ALONE, at most 3 per run; a TIMEOUT or hung unit is never replayed), `CADRE_GATE_FILE_TIMEOUT` (default 1800 s per unit), `CADRE_GATE_TIMEOUT_BIN` (seam of the runner called alone, purged by `verify.sh` — see the purge below). Each gate that ran a step appends ONE row to `.agents/state/local/porte-chrono.tsv` (an observation, never read by a verdict): start, seconds, sha, mode, rc and, since T-01M5PVWF7H, a 6th column naming the FIRST red step (`-` on a green; under `--at` the frozen clone's inner run hands its label back through a file of the clone, read at most 200 bytes, never through a symlink); `?` when no step could be noted, or when the label carries a control character. A FATAL exit before the verdict (the `--linux` leg's extractions from `ci.yml`) notes `?` only when no step was red before it: a live run under `CADRE_GATE_FAIL_FAST=0` that hits it after a red step keeps that step's label, and under `--at` the inner run writes its label to the clone's file the moment it is noted, so a FATAL exit keeps the label already noted. `specs.py chrono --etapes` reads 5 or 6 columns and prints the reds per step, « non noté » for a 5-column row. Use the gate instead of a hand-picked `pytest <dirs>`: `pytest.ini` owns the scope and a selected subset silently tests something else. The `--linux` leg matters because CI is ubuntu while this kit runs on Windows dev boxes and several of its mechanisms encode MEASURED Windows semantics — three consecutive pushes went red on that gap alone (L-00000068). A test that measures a platform fact is MARKED `skipUnless`, never loosened: an assertion weak enough to pass everywhere measures nothing. **The long replay runs on a FROZEN checkout: `--at <ref>` (typically `--at HEAD`) verifies a sibling frozen CLONE detached on that ref, not the live tree.** The verdict is then ANCHORED TO A SHA (`VERIFY OK @ <sha>`), which is what makes it mean anything — hence the **push rule: only a SHA whose verdict came back green may be pushed**; commits landed since, and you push the green ancestor or re-verify the new head. During an `--at` run the live tree is NOT measured and stays entirely free, read AND write — keep working, commit, switch branches; the one thing forbidden is writing into the verification clone (a clone, not a `git worktree`: a linked worktree's `.git` is a pointer file holding an absolute HOST path, unreadable once the tree is mounted in the `--linux` container — measured, it made the first dogfood run red). That freedom is specific to `--at`: a run WITHOUT it measures the live tree, so "a verification gate must see a stable tree" still holds there — reserve the bare form for quick host checks. The further rules below are all paid for in wasted pilot time rather than deduced:

**AVANT DE POUSSER, RAFRAÎCHIS LE RELEVÉ CI — c'est l'ÉCRIVAIN du canal, et le canal n'a pas d'autre écrivain.** `bash core-scripts/ci-last-run.sh` interroge `gh` pour le dernier run de CHAQUE workflow sur `main` et écrit `.agents/state/local/ci-status.line`. Le SessionStart, lui, ne lit que ce cache (`--cached`) : zéro réseau, zéro attente au démarrage — donc **si personne ne lance cette étape, la ligne injectée vieillit indéfiniment et le mécanisme devient inerte**. Le moment est choisi : avant un push on s'apprête de toute façon à attendre, et l'état de la CI est précisément ce qu'on a besoin de savoir. Le mur est borné dans le script (8 s + 1 s par workflow) et `gh` absent dégrade en l'ANNONÇANT, jamais en silence. La ligne rendue porte l'ÂGE du relevé : un cache jamais rafraîchi se lit « il y a 3 j », pas « absent » — la péremption est visible plutôt que devinée. Un canal se vérifie aux DEUX bouts ; celui-ci a son lecteur au SessionStart et son écrivain ICI. [L-00000136, T-00000379]

**CAPTURE THE WHOLE OUTPUT, NEVER PIPE A VERIFICATION THROUGH `tail`/`head`.** The cause of a failure sits in the MIDDLE of the log — the last lines carry only the verdict. A run backgrounded as `verify.sh … | tail -10` came back red with nothing but `pytest rc=1`, every failing test name already discarded at the source, and the container had to be replayed for six minutes to recover information that had been produced once (L-00000140). The background mechanism ALREADY writes the full output to a file and hands you its path: pipe nothing inside the command, then read, `grep` or tail that FILE. In the foreground, redirect (`cmd > out 2>&1`) and read afterwards. This holds for anything that VERIFIES — a gate, a build, a test suite, a scan: a truncated capture turns a diagnosis into a guess and costs a full re-run.

**A verification BY ABSENCE goes through ripgrep, never `grep -P` via the shell.** On a Windows box `grep -P` dies with "supports only unibyte and UTF-8 locales" on a non-UTF8 locale, and it dies SILENTLY — measured elsewhere as 3 false negatives out of 11 findings (L-00000141). Much of this kit's guard surface is exactly that shape (no secret, no machine path, no hex outside the tokens, no ungated call), and an absence check that fails quietly returns a green that measures nothing — the worst failure mode a guard has. Use the host's BUILT-IN search tool (`Grep` on Claude Code, and its equivalent elsewhere); if a shell is unavoidable, check the exit code AND prove non-vacuity on a case that must match.

**The built-in tool is the CANONICAL instrument, and the shell binary is a conditional fallback — INSTALLING ripgrep is therefore never a prerequisite of this kit.** The distinction is not cosmetic and it was paid for: the built-in tool is ripgrep already, shipped with the host, so it is present on every machine by construction and it fails LOUDLY; the standalone binary on `$PATH` is a separate, optional install that fails BY THE VOID when absent — `rg PAT || echo NONE` takes the failure branch on the 127 of command-not-found and prints NONE, `rg PAT 2>/dev/null` swallows the message and prints nothing, and both outputs have exactly the shape of a search that found nothing. So a machine adopting this kit needs NO setup step here: an agent that reaches for the built-in tool is correct everywhere, and the `safe-bash` guard exists precisely so that the shell form REFUSES rather than lies when the binary is missing. Installing it is a convenience for humans working at a terminal, never a condition of the kit running. Measured on this repo the day the rule was written: the maintainer's own box carried no `rg` on `$PATH` — only a copy buried inside an editor's `node_modules` — while every absence check made through the built-in tool had been sound all along.

**A guard must never block its own diagnostic.** Corollary of the above, and a defect this repo shipped for one commit: the `rg`-absent guard refused `command -v rg`, the single command that establishes whether the tool resolves — because `command` is a wrapper and so keeps the command position open, making a PRESENCE PROBE indistinguishable from an execution. A probe (`command -v X`, `which X`, `type X`) prints a path or fails; it never runs X, so it cannot produce the failure mode any of these guards is built to catch. When you add a guard, check what it does to the command someone would run to find out WHY it fired: a guard that blocks its own diagnostic converts a two-second check into an investigation.

**FAST RED, AND THE TEMPLATE'S PREREQUISITES, BEFORE THE DELIVERY GATE** (pilot decision S-01M4WTZ1QZQJZZNYRC5YA67AZW, 2026-10-14). A delivery runs ONE gate, AFTER its delivery branch `<L>` is merged into its target — `git merge --no-ff <L>` from the main checkout, step (9) of the delivery order in `.agents/skills/kickoff/SKILL.md` § ONE REVIEW WAVE PER DELIVERY — anchored on that merge's sha (`verify.sh --at HEAD`, plus `--linux` where your push rule asks for it). Never a gate on `<L>` before the merge: its green anchors the sha of `<L>`, not the merge's, and `.githooks/pre-push` compares the pushed sha with the stamp's, so the push would need a second gate. Give that gate `CADRE_GATE_BASE=<sha of the target before the merge>` — `git rev-parse <target>` read before the merge, or `HEAD^1` right after it, since the first parent of a `--no-ff` merge is the target as it was: the priority phase then plays the delivery's own files first, so a red there comes out in minutes instead of at the end. On a GREEN priority phase the full suite still runs; on a red one, under `CADRE_GATE_FAIL_FAST=prio` (the default), the rest of the suite and the later steps are NOT run — the gate is red and says what it skipped; `CADRE_GATE_FAIL_FAST=0` plays everything. Under parallel legs a pytest red stops the bash leg (`NOT RUN`), as in series. Not `$(git merge-base <target> HEAD)`: after the merge it is HEAD itself, and the priority phase is empty. Bound: the priority phase exists on the parallel host leg only (`CADRE_GATE_JOBS` other than 1, `auto` by default on the host) — the bare form and the `--linux` container leg, which receives only `APT_PKGS`, `CADRE_GATE_JOBS` and a fixed `CADRE_GATE_DURATIONS_DIR=/tmp/porte-durees` (the `docker run` line of `verify.sh`), never `CADRE_GATE_BASE`, ignore the base. Between the closing review and the `done`s, no OTHER frozen green gate of any lane may land: `VERIFY_STAMP.log` is shared by every lane, and the review's freshness is judged against its second-to-last frozen green (a replay on the same sha does not count) — otherwise relaunch the critic. Before a gate that precedes a template sync, run `sync_template.py --source <branch> --check` and the build-staleness probe, which `--check` does not play (`git merge-base --is-ancestor $(git log -1 --format=%H <branch> -- .agents/ui-src/) $(git log -1 --format=%H <branch> -- .agents/ui/)`: rc 0 = fresh, otherwise `--apply` exits 19), and push the source branch as soon as its gate is green — `--apply` refuses a source branch absent from the remote. The template's own adopter gate is short; what costs is replaying the kit gate, so every refusal you can find before it must be found before it. A red gate at closure enters the boucle de réparation bornée of kickoff (`.agents/skills/kickoff/SKILL.md` § La boucle de réparation bornée (porte rouge)): 3 tentatives at most, each traced `--kind delta` avant de rejouer and replayed under `CADRE_GATE_FAIL_FAST=0` so that two counts cover the same scope, arrêt si les erreurs augmentent (k_n > k_(n-1)), then escalade `communicator`; une porte tuée n'est pas une porte rouge (replayed once, no attempt spent); `/night` hors portée. Where reds fall is MEASURED before the gate is shortened (T-01M5PVWF7H): after 5 frozen red gates noted at 6 columns, a widened base (the last green gate) opens only if the median red still lasts ≥ 70 % of the median green, and must not slow the median GREEN gate by more than 5 %; a pre-gate of the bash suites opens only if at least 3 of those 5 reds name `bash core-scripts/run-bash-tests.sh`, and its witness inherits, on purpose, each of the five settings `verify.sh` purges at entry (the CLOSED list below). Of the slow benches, `semgrep-scan.test.sh` and `gitleaks-scan.test.sh` are each split in two halves (`semgrep-scan-git.test.sh`, `gitleaks-scan-index.test.sh`, T-01M55Z3W38NDBXMTZBP81GKA8R), played side by side on the parallel host leg only (`CADRE_GATE_JOBS` other than 1; CI and the bare form play them in series, and so does `--linux` by default). No gain is shown: measured once on the kit's station (2026-10-26, n=1), the bash leg went from 557 s to 547 s — it is bound by CPU contention, not by one suite (the semgrep half: 281 s alone, 547 s among the others). Bound: a change to `semgrep-scan.sh` or `gitleaks-scan.sh` puts only the head half in the priority phase; the other half plays with the rest, where its red still counts, but only at the end (T-01M5TC4AM9TPTSMD439K79BHXS). `test_session_banner` goes to T-01M5TC4BY6KENX5SKM73C645Y9 on the pytest leg; `test_docs_only_route_contract` is not attributed yet.

**A RED GATE, THEN `--rouges`, THEN THE FULL GATE — the only one that lets a push through** (T-01M5QBFKM444FB53RM2J1NBB4X, pilot decision S-01M5QBG09B3R1NDJPZATE7NCDT; kit and adopter alike for the purge, KIT ONLY for `--rouges`). A RED full gate (live or `--at`) writes (a FATAL live exit writes none) `.agents/state/local/PORTE_ROUGES` (git-ignored, local): `# porte-rouges v1`, `sha=` (40 hex), `mode=live|frozen|frozen-linux`, `at=`, then one `<kind><TAB><entry>` line per red — `pytest <file.py>` and `bash ./<suite>` come from the two runners, which write the units they PLAYED and left red into the file `verify.sh` hands each step as `CADRE_GATE_ROUGES_OUT` (a rerun-green unit and a NOT RUN one are never listed); a red with no runner line is `etape <label>`. Under `--at` the frozen clone writes it and the outer run re-reads it only if it is a regular file of at most 64 KiB naming that sha, otherwise `etape ?`. Every full gate ERASES it at its entry (live: right after the arguments; `--at`: once the lock is held), so a gate killed before its verdict leaves nothing to replay; while an `--at` gate's lock exists (`<WT>.lock`), `--rouges` on an absent list says `une porte --at tient <lock> et a effacé la liste — attends son verdict` (rc 2), never « play the full gate » beside it. Fix, then `bash core-scripts/verify.sh --rouges` (alone: refused rc 2 with `--at`, `--linux`, under `VERIFY_INNER=1` and in an adopter's gate) replays on the LIVE tree, each entry through its own runner — one `run-pytest-shards.sh --only <file>…` call (`--only` restricts the collection, never takes the bare `exec`, every listed file must be collected), one `run-bash-tests.sh --only <suite>` per suite, the three host step labels replayed whole — and prints `REJEU VERT` (rc 0), `REJEU ROUGE` (rc 1) or `REJEU INCOMPLET` (rc 2: an `etape linux replay`, `porte adoptant` or `?`, an invalid path, a runner that refuses (a pytest collection in error — a broken import, rc 2 with « la collecte nue rend rc=2 » — is a played red, `REJEU ROUGE`), a `bash` entry whose suite announces a SKIP, `pytest` entries whose files played no PASSED test — all skipped, judged on the TOTAL of the one runner call, never per file: an all-skipped file listed next to a file that passes is credited, and xfail or a partial skip are not seen; an `etape` replayed whole is judged on its rc, like the gate's step). The replay is NOT a verdict: it writes no stamp and no chrono row, and the list must be of HEAD's lineage (`git merge-base --is-ancestor`). Then the full gate, `bash core-scripts/verify.sh --at HEAD --linux` (on this repository `--at HEAD` alone), and only its green is pushed. **The purge at entry, every mode — the adopter's gate (`porte_adoptant.py`) included:** `BASH_ENV`, `BASH_TEST_TIMEOUT_BIN`, `CADRE_GATE_TIMEOUT_BIN`, `PYTEST_ADDOPTS`, `PYTEST_PLUGINS` — each MEASURED crediting a PASS without playing — are unset, and each one found set is said on stderr, `verify.sh: réglage purgé à l'entrée : <NAME>` (an adopter who sets `PYTEST_ADDOPTS` or `BASH_ENV` for its own tests sees it go, never in silence; a `BASH_TEST_TIMEOUT_BIN=gtimeout` on a macOS without `timeout` is lost too: `COVERAGE DEGRADED`, suites still played). That list is CLOSED, never « every setting »: NOT purged and NOT covered, an OPEN list — `PATH`, `PYTHONPATH`, `ENV`, exported functions (`BASH_FUNC_*`, and a `BASH_ENV` that redefines `unset`, which bash sources before the purge — measured: the whole purge cancelled), the tree's own conftest or plugins. BOUND: the adopter's CI leg (`.github/workflows/ci.yml` runs `python .agents/bin/porte_adoptant.py` directly) is NOT purged — `porte_adoptant.py` is purged only when `verify.sh` launches it. Witness: `core-scripts/verify-rouges.test.sh`.

**THE TEMPLATE IS VALIDATED IN A FRESH CLONE, BEFORE ANY PUSH** (pilot decision S-01M54V11JAR8YQWWRWQHADBRDR, 2026-10-17) — KIT TEAM only: an adopter has no `template/starter-kit` to sync. `sync_template.py --apply` never commits nor pushes: commit LOCALLY on that branch, then, as an adopter, `git clone --branch template/starter-kit <kit repo> <clone>` (under `/tmp/`) and `git -C <clone> config core.hooksPath .githooks` (a clone has none: no hook runs, measured). From the clone's root: `python3 .agents/bin/setup_projet.py`, the adopter gate `bash core-scripts/verify.sh --at HEAD` (green: the clone's own `VERIFY_STAMP`, `porte=adoptant`) and the WHOLE `pytest .agents/evals`. Green: push FROM THE CLONE, `git -C <clone> push <forge URL> HEAD:template/starter-kit` (its `origin` is the local kit). Never from the sync's copy: its `pre-push` reads that copy's own stamp, with no gate for this sha. Red: fix the kit, sync again.

Between two tries, never `reset --hard` nor `git clean -f…` (`safe-bash` refuses both, `-C` included): `git -C <clone> fetch origin`, then `git -C <clone> reset --keep origin/template/starter-kit` — measured, it reaches the new tip, refuses when a tracked edit or an untracked file sits on a path the two tips differ on, and cleans nothing: other edits, untracked and ignored files stay. So if `git -C <clone> status --porcelain --ignored` prints anything (a green gate always leaves its stamp in the ignored `.agents/state/local/`), reclone: under `/tmp/` the Claude guard accepts `rm -rf <clone>` (safe_bash.py refuses it, invoked directly: Codex at runtime, Copilot inherited, Kimi assumed, Gemini inert G0); where it refuses (measured under `~/.local/state/`), deleting it is the pilot's gesture. Bound: a PROSE rule — no guard refuses a template push without that green clone today; T-01M54W64S47FS02G0XCGPY8D4X is the mechanical task.

**THE PUSH RULE HAS A MECHANICAL REMINDER NOW — AND "REMINDER" IS THE EXACT WORD, NOT A HEDGE.** `VERIFY OK @ <sha>` used to go to stdout and nowhere else, so the rule above stayed a habit: a mechanism whose return channel is discarded does not exist. Every verdict now also writes `.agents/state/local/VERIFY_STAMP` — five lines, `sha=` (full 40 hex) / `mode=frozen|live` / `linux=0|1` / `host=` / `at=` — and `.githooks/pre-push` reads it, per ref line git feeds it, refusing when there is no stamp, when it is malformed, when `mode=live` (a live-tree run is not anchored), or when its `sha` is not the one being pushed. A host-only verdict (`linux=0`) is ACCEPTED and the uncovered leg is ANNOUNCED, because ubuntu is the non-blocking CI leg; `git config --bool verify.requireLinux true` makes it blocking. Every refusal prints its remedy, and every verdict now prints one status line saying whether the hook is actually wired — a hook FILE that exists is not a hook that RUNS, and nothing else in a repository tells you which of the two you have. **What this is NOT: a gate.** The stamp is local, git-ignored and UNAUTHENTICATED — a five-line `printf` fabricates it in three seconds, and `git push --no-verify` walks past the reader entirely — `safe-bash` refuses that form to an agent (rule `git-hooks-bypass`), never to a human at a terminal, and its own bounds are named in `.agents/ref/PORTES_REFUS.md` § safe-bash. **It attests a discipline; it proves nothing.** The word *gate* is reserved for the forge-side ruleset in `.github/rulesets/`, which only the pilot can activate and which a `403` on a private repo without a paid plan can make impossible. **The ceiling is BOUNDED, not enumerated**: `--no-verify`, a hook never installed, a forge without the plan, and tag pushes (an annotated tag's local sha is the tag object, not a commit, so the hook declines to gate it and says so) are the holes we KNOW — the list is not closed.

**INSTALLING IT IS WRITTEN BY WHAT IT DISABLES.** `core.hooksPath` REPLACES `.git/hooks/` in its entirety; it does not add one hook. The machine and project setups check the repository, `.githooks/`, effective `core.hooksPath`, and active non-`*.sample` entries in the real Git hooks directory before offering local activation. With an input TTY, outside `--dry-run` and with no agent marker set (`CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `AGENTS_HOOK_HOST`, `COPILOT_AGENT_SESSION_ID`, `COPILOT_CLI`; Codex, Gemini and Kimi set none in the agent's shell), they ask exactly `Activer les hooks de ce dépôt (tous ses worktrees liés partagent ce réglage) dans .githooks ? core.hooksPath remplace les hooks de .git/hooks ; pre-push refuse un push sans tampon de porte vert ; commit-msg refuse certains sujets ; Git exécute les hooks de l’arbre courant. [o/N]`. Only exact lowercase `o` or `oui` sets `core.hooksPath=.githooks`; Enter, EOF, `Non`, `Oui`, `OUI`, and ` o ` mean No. A foreign hooksPath, missing `.githooks/`, failed Git read or active hook prevents the question and any config or hook write. To inspect manually:

```bash
git config --get core.hooksPath          # effective setting; a foreign value stays in place
git rev-parse --git-path hooks           # inspect this Git directory, resolving relative paths against the repository root
```

With no active hooks, you may accept the setup's question (default No) or, after the same check, set `git config core.hooksPath .githooks` locally. With active hooks, integrate them into `.githooks/` and chain matching names; or integrate the kit hooks into the active hooks directory without changing `core.hooksPath`. If a `pre-push` already exists, chain the two `pre-push` hooks; never copy the kit's over the existing one. On THIS repo the damage would be nil — measured, `.git/hooks/` holds 14 `*.sample` and zero active hooks — **and that is precisely why nobody would notice the rule being wrong.** To undo local activation — the PILOT's gesture, by hand: `safe-bash` refuses it to an agent (rule `git-hooks-bypass`, T-01M5C1AF6GB3ZRX5QF9SF6R80Y) — check that the value is still the one set by the setup before `git config --unset core.hooksPath`. If you manually integrated kit hooks into another directory, review and remove only that integration; an orphaned kit `pre-push` left after `verify.sh` is reverted refuses every push, since no run writes the stamp it waits for. The kit offers the hook and activates it only after the check and the operator's exact opt-in.

**Two lessons this mechanism encodes, cited in clear because they are the ones people re-derive the hard way. L-00000344** — the gate is anchored to the sha of YOUR commit, so the order is: commit the write-set, then `verify.sh --at <sha of THAT commit>`, then read the whole file, then expect `VERIFY OK @ <that same sha>`; and once the proof needs a commit, the rollback is `git revert <sha>` and NEVER `git checkout -- <paths>`. **L-00000345** — `--at` and `--linux` are ORTHOGONAL: `--at` alone never replays the container, so a gate that must cover the linux leg is always written with BOTH flags named, `bash core-scripts/verify.sh --at <sha> --linux`, output captured whole and never through `tail`/`head`. Then push that sha — and, the first time, push it THROUGH the installed hook, so the reminder is observed working rather than assumed.

**AN ANNOUNCED STOP IS NOT A PROOF OF DEATH — LOOK FOR SURVIVING CHILDREN (`ps`) BEFORE CONCLUDING A RUN IS OVER.** Measured twice in one evening on `verify.sh --at`. Once, a killed run left its lock behind and every later run refused for no reason. Worse, once a run believed dead was ALIVE: the stop had killed only the SHELL WRAPPER while its children — the frozen clone's own `verify.sh`, then `run-bash-tests.sh` — kept running and kept holding the lock legitimately, and only a well-aimed `ps` revealed it. A mechanism that stops a long task stops the process it LAUNCHED, not the process TREE below it. So: after stopping a long run, look for residue (`ps`) before touching anything that run owned, and NEVER free a lock, wipe a workspace or start a second run on the sole faith of a stop reported successful. Corollary now enforced in code (T-00000128): the `--at` lock records its holder's PID and take-time, decides alive-versus-abandoned itself (reclaiming a dead holder's lock automatically, announcing it), and is released only BY that holder — a lock a script cannot attribute is a lock no script should free.

**A GATE KILLED BY THE MACHINE HAS NO VERDICT — ON THE WORKSTATION WHERE THIS WAS MEASURED, THE LEVER WAS THE CONTAINER RUNTIME'S MEMORY CEILING, NOT THE HOST LEG.** Measured on the kit's workstation on 2026-09-14: two `verify.sh --at HEAD --linux` runs died during the container leg, killed by the harness's memory watchdog and not by the kernel, whose log therefore stayed empty — which first read as "no memory kill at all" (L-00000462, rectified by L-00000463). A killed gate prints neither `VERIFY OK` nor `VERIFY FAIL`: it is told from a green only by whoever reads why the run stopped. The host leg was not the cause: the full pytest peaked at 208 MiB (`ru_maxrss` 217 743 360 bytes). The Linux VM had been granted 15.6 GB (`docker info` MemTotal) and was logged at 4 753, then 5 072, then 5 217 MB during the gates, still growing (readings recorded with T-00000613). The remedy is a PILOT gesture outside the repository, not a rule for every adopter: lower the runtime's memory ceiling (Docker Desktop: Settings › Resources › Memory; colima: `memory:` in `~/.colima/<profile>/colima.yaml`, then `colima stop` and `colima start`). ## Section adoptant — the adopting project's push gate (T-00001183)

Everything above describes the KIT's gate. In a project that adopted the kit, the verdict is the project's own build and tests, submodules included — never the kit's suite (pilot decision S-00004119). For an adopting project this section supersedes the « les deux drapeaux voyagent ensemble chez l'adoptant » of the verbatim snapshot at the end of this file.

**The mode, one rule in three places.** ADOPTANT iff `.agents/IS_THE_KIT` is absent AND `.agents/security/module_discovery.py` is present — the same test in `core-scripts/verify.sh` (`porte_mode`), `.githooks/pre-push` and the `porte` job of `ci.yml`; a pyproject's name never enters it. Under `--at` it is decided on the FROZEN clone, never on the live tree, and `verify.sh` prints it (`porte: adoptant …`). **The presence of `.agents/IS_THE_KIT` therefore ALSO switches the push gate to the kit's suite** — and a `cp -r` of the kit brings that file along (`QUICK-SETUP.md`: delete it). On `pull_request`, the `porte` job reads the base too (`HEAD^1`, `fetch-depth: 2`): a PR that takes an ADOPTANT base out of adoptant mode — the marker added, or the discovery removed — is RED, named, before any output is written; a base it cannot read is RED. Nothing refuses a tree that was never in adoptant mode.

**What runs.** The kit's three steps give way to ONE step, `.agents/bin/porte_adoptant.py` — absent, it is RED and named, with its remedy (synchronise `.agents/bin/porte_adoptant.py` with `core-scripts/verify.sh`, same kit commit), never a fall back onto the kit's suite. **The project's own script first:** if `scripts/verify-projet.sh` exists at the root AND is tracked by git, it decides for the WHOLE repository (pilot decisions S-00004250 and S-00004278): the gate runs it (`bash scripts/verify-projet.sh`, cwd the root, the gate's environment with `GIT_*` removed — nothing else is removed) and ITS rc decides, 0 being green; NO default sequence runs, not for the root, not for a nested module, not for a submodule — the guards still run and still block. Present but untracked, it is set aside, named, as if absent. A script that calls `verify.sh` or the gate back does not loop: `PORTE_ADOPTANT_EN_COURS`, set by the gate and inherited by its children, makes the nested gate RED, named. **No script and no module of a known family** (npm, python, java, swift — a PHP-only project, say): the gate does NOT block — the guards alone judge, and a named warning is printed and written to the result (`avertissement=build et tests non vérifiés par le kit : ajoutez scripts/verify-projet.sh`), copied into the stamp by `porte_lire` and PRINTED by `.githooks/pre-push` at the push (`pre-push: WARNING in this verdict — …`) — an output, never a refusal. **A MIXED repository is warned too** (binôme c4f3 ter): without a tracked script, a TRACKED manifest of an ecosystem outside the table (closed list: `composer.json`, `go.mod`, `Gemfile`, `Cargo.toml`, `mix.exs`, `*.csproj`, `*.sln`, `build.sbt`; `git ls-files` at the root and in each populated submodule, outside what the discovery prunes) is NAMED in that same warning even when known families run (`manifeste(s) hors table (composer.json) : …`, ten names at most, the rest counted); with no known module either, both messages make ONE value on one line — no rc changes; an ecosystem missing from the list, or an untracked manifest, is not seen. Otherwise, for every module `module_discovery` finds, a closed table of commands (a known family that FAILS stays RED): python, `pytest -c <the module's own config | a generated ini> --rootdir <M> --confcutdir <M>`; npm, the install the module's LOCKFILE names — `pnpm-lock.yaml` → `pnpm install --frozen-lockfile`, `yarn.lock` → `yarn install --frozen-lockfile` (header `# yarn lockfile v1`, or unrecognised) or `--immutable` (Berry, `__metadata:` in column 0), RED when the install rewrites `yarn.lock`, `package-lock.json` / `npm-shrinkwrap.json` → `npm ci`, in that precedence, printed when several coexist; no lockfile is RED (« aucun lockfile : la porte n'installe pas sans verrou ») — then `<manager> run lint|test|build`, a manager absent from PATH being RED, named; java, swift. Then gitleaks on the root and on each populated submodule, semgrep on what is NEW only (next paragraph), and a short integrity check (the hook scripts the registries cite exist, `bash -n` on them and on `.githooks/`, `.githooks/pre-push` executable in the index). It installs a dependency only through an npm module's lockfile, and plays no `test_*.py` of the kit. Its verdict comes back through `.agents/state/local/PORTE_RESULT` (`sha=`, `verdict=OK|ECHEC`, `modules=`, `derogation_*`, `avertissement=`): a green step whose `PORTE_RESULT` does not name THIS sha and say `OK` is RED.

**SAST: only what is new blocks** (pilot decisions S-00004250 and S-00004276). semgrep runs with `--baseline-commit <base>`; only the findings ADDED since that base block, the pre-existing ones are the project's debt, to be fixed in a task of their own (security-gate doctrine). **The root's base is IMPOSED** through `CADRE_SEMGREP_BASE` when the caller knows it: `verify.sh --at` computes it on the LIVE tree (`git merge-base <sha> <default branch>`, same ref order as below) — never in the frozen clone, whose `origin` IS the live tree and whose `origin/HEAD` named the branch the live tree had checked out (measured: base `HEAD^1`, an `eval` in commit 1 of 2 passed); `--at` also removes that `origin/HEAD` from the clone. The CI `adoptant` job passes the PR's base on `pull_request` and `github.event.before` on `push` — every pushed commit judged — through `env:` only. The gate takes an imposed base only if it is 40 hex AND an ancestor of HEAD (equal to HEAD: `HEAD^1`); otherwise — a branch creation (`0000…0`), a force-push (`before` gone or not an ancestor), a malformed value — it falls back, and says so. **Without an imposed base**, the gate computes `git merge-base HEAD <default branch>`: `origin/HEAD` resolved, then `origin/main`, `origin/master`, then the local `main`, `master`; HEAD ON or BEHIND it (merge-base = HEAD): the base is `HEAD^1`, so only the last commit is judged. **A submodule's base is its gitlink at its parent's base** — what the change brought into it; a submodule absent at that base, or whose gitlink is not an ancestor of its HEAD, falls back on its own computed base, said. Bound, named, not fixed (opus N3, pilot decision pending): a submodule ADDED by the judged change has no gitlink at the base, so the fallback most often judges only its last commit (`HEAD^1`) and a finding in its earlier commits passes. No computable base (truncated history, no default branch): a FULL scan, and the gate says so. **A file whose partial reading semgrep REPORTS is a refusal, not a clean**: the gate reads semgrep's JSON report (`--json-output`), and a non-empty `errors` (`PartialParsing` included, level `warn`, rc 0 — measured, an `eval` became invisible) is `COVERAGE DEGRADED — semgrep n'a pas lu en entier N fichier(s) : …`, RED unless `CADRE_GARDES_DEGRADEES`; a missing report likewise. What semgrep recovers WITHOUT reporting it passes (measured, semgrep 1.175.0: JavaScript holding only `function (` or `const y = ;` gives `errors: []`, scanned, rc 0). Bounds, measured on semgrep 1.175.0: an UNTRACKED file, and a pre-existing file read only in part, are not seen under a baseline; an unreadable base sha is an ERROR (rc 2), which `CADRE_GARDES_DEGRADEES` can cover. The CI `adoptant` job checks out with `fetch-depth: 0` so that the merge-base exists, points `origin/HEAD` at the repository's default branch before the gate (`git symbolic-ref`, the name by `env:` — the checkout sets none, per the binôme c4f3, not re-measured here), so that a default branch outside `main`/`master` still gives a merge-base when the imposed base is refused, and runs `corepack enable` (pnpm, yarn) before the gate. gitleaks still reads the whole tree.

**The stamp and the push.** The stamp carries `porte=adoptant`, each traced `derogation_*`, the gate's `avertissement` if any, and `linux=0` whatever `--linux` said: the container leg replays the KIT's suite, so in this mode `--linux` has no object and docker is never called. The push rule reads `bash core-scripts/verify.sh --at <sha>` — the both-flags form of L-00000345 is the KIT's rule. In this mode `.githooks/pre-push` refuses a stamp without `porte=adoptant` (the kit's suite wrote it), does not apply `verify.requireLinux`, and prints every traced derogation.

**Two traced exits, each with a non-empty reason** (a flag such as `=1` is refused; control characters are stripped, 200 code points at most): `CADRE_GARDES_DEGRADEES` — a scanner absent or in ERROR, or a file semgrep read only in part, never a finding; `CADRE_SANS_TEST` — a module without a test. A gitleaks or semgrep FINDING has no exit. `CADRE_SANS_MODULE` is still read and validated the same way, but has NO OBJECT since S-00004278 (« no module » is a warning, not a refusal): it is announced as such and `derogation_module=` is never written.

**`--at` populates the submodules FROM THE LIVE TREE, at the sha of their gitlink, never from the network.** A clone has no submodule, and a frozen checkout of a project whose modules are submodules would be judged over empty directories. `peupler_sous_modules` (`verify.sh`) checks that each `.gitmodules` path is the root of an initialised repository in the live tree, points the clone's submodule URL at that live path (the `.gitmodules` URL is never read), and runs `git submodule update --checkout --force` under `GIT_ALLOW_PROTOCOL='file'` — any other transport, `https` included, is refused — recursing by hand into nested modules; `peupler_et_verifier` then cleans every module and reads `git submodule status --recursive` as the last line of defence. A no-op without `.gitmodules`.

**NO derogation covers a population refusal.** Each exits rc 1 ABOVE the stamp and `porte_adoptant.py` is never launched, so none of its exits can apply. The refusals, as `verify.sh` prints them after `--at: `, and their remedies:
- `sous-module à espace dans le nom ou le chemin (« <line> ») — non pris en charge` — refused BEFORE the `.gitmodules` line is split, which would have produced a wrong path and a wrong remedy; rename the submodule and its path without a space (the gate also refuses any path outside `[A-Za-z0-9._/@+-]`).
- `sous-module '<path>' non initialisé dans l'arbre vivant (<live>/<path>)` — remedy printed with it: `git -C '<live parent>' submodule update --init -- '<path>'`, rooted at the PARENT module (without `-C` it fails at depth 2 from the root, measured).
- `git submodule update a échoué dans <clone> (…)` — the cause is in the git lines above it. A pinned sha absent from, or not advertised by, the live module: **make it reachable from a branch or HEAD of that live module**, then rerun. `failed to unpack tree object` or `cannot checkout new HEAD` inside a module: a GLOBAL git setting read by the child gits (next paragraph).
- `refus — un sous-module n'est pas au sha épinglé (ligne de défense : git submodule status --recursive)`, followed by its `-` (not initialised), `+` (not at the gitlink) or `U` (conflict) lines.
- The gate itself also judges the submodules of the tree it runs on — the live tree without `--at`, the populated clone under it — RED and named: `sous-module non peuplé` (empty directory), `sous-module désaligné` (HEAD ≠ gitlink), `sous-module modifié` (uncommitted tracked changes).

**Prerequisite.** `protocol.file.allow=never` in GLOBAL git config already breaks `--at` at the `git clone`/`git fetch` of the superproject, before any population — leave it at `user` (git's default) or `always`.

**What `--at` isolates, and what it does not.** It isolates its child gits from `submodule.recurse` (and, through it, `fetch.recurseSubmodules`): `-c submodule.recurse=false` travels to the children, re-posed at every level, while the `--no-recurse-submodules` of its four `fetch`/`checkout` lines protects the parent only; and from `submodule.<name>.update`, through `--checkout`. Any OTHER global setting read by a child git is NOT neutralised: at worst it gives a refusal — the line of defence reads every module's sha — and the message is not guaranteed to name it. List what applies with `git config --global --get-regexp '^(submodule|fetch)\.'`.

**Scope, written so it is not re-read as universal.** Population, the four flags, the transmission of `-c` to child gits and the refusal of an unadvertised object were measured on git 2.55.0 / macOS only. Linux, older gits (below 2.26 protocol v2 is not the default) and Git Bash / Windows are NOT measured: a named refusal there is the expected default, not a measurement.

Une vérification n’est **jamais** tronquée par `| tail` ou `| head` : la cause est au milieu du log, le verdict seul est à la fin. **Deux gates ne tournent jamais en parallèle** — la contention de la machine produit des faux rouges sur les tests de temps. **La forme qui ANCRE est `--at`** — la forme nue mesure l’arbre vivant, écrit `mode=live`, et ce verdict est REFUSÉ au push ; tape `bash core-scripts/verify.sh --at HEAD --linux` avant tout push, et les deux drapeaux voyagent ensemble **chez l'adoptant**, puisque `--at` et `--linux` sont ORTHOGONAUX — `--at` seul ne rejoue jamais la jambe conteneur. **PORTÉE, écrite pour ne pas être relue comme universelle** : sur CE dépôt, une dérogation pilote datée (2026-09-14, `PLAN-ETAT.md` § 4, surface qui ne voyage pas) joue `--at HEAD` seul ; le code l'accepte — `.githooks/pre-push:216` prend `linux=0` sauf `verify.requireLinux=true` — et la jambe conteneur a coûté 10 min 52 mesurées le 2026-09-20. Là où les deux surfaces divergent, c'est le § 4 local qui s'applique ici, et cette phrase-ci qui s'applique chez l'adoptant. → détail : `.agents/skills/verification-discipline/SKILL.md`
